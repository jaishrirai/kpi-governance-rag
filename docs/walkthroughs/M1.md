## Why V3 has 52 chunks, not 50

V3 is one chunk per document. The POL-04 glossary table is too long for the 450-token cap, so it splits into 2 chunks. 50 + 2 = 52.

## Key logic

Manifest first. Metadata (owner, certification, doc type) comes from the manifest, so the YAML header is not needed for it.

PDF headings come from font size. Bold at 16pt or more is `#`, bold at 12pt or more is `##`.

Tables are read cell by cell. Each row becomes `ID: KPI-001 | Owner: ... | Status: ...`, so a value always stays next to its label.

Token estimate is characters divided by 4. The cap is measured with the header included, because the header is part of what the embedding model sees.

Cuts prefer line breaks, then spaces. A table row is never split in half.

## Decision: POL-04 table format

Three options were measured on the glossary table.

| Option | Format | Tokens | Chunks |
|---|---|---|---|
| Scrambled text (pypdf, earlier) | cells run together | 664 | 2 |
| A. Labels on every row (kept) | `ID: ... \| Owner: ...` per row | 816 | 3 |
| B. Header once | column names once, then values | 618 | 2 |
| C. Labels on Owner and Status only | partial labels | 681 | 2 |

We keep A. Owner and status stay unambiguous, which matters more than the extra tokens. The cost is one more chunk under V1.

## Interview questions (answered)

1. Why does the loader read the owner from the manifest, not the YAML? The manifest is the single source of truth and holds the owner, certification and doc type. YAML is mostly body text and headings are removed.
2. Why does `load_pdf` use font sizes to find headings? Size shows the structure of the page without needing the wording, so section and subsection context is kept.
3. Why does V2 average 55 tokens and V3 240? V2 cuts at each heading, so each chunk is one section. V3 keeps the whole document together.

## Step 1.5 results: embeddings and Chroma (real run)

Build: `python -m rag.index --variant all` stored 52, 230 and 52 vectors (kpi_v1, kpi_v2, kpi_v3). Chunks over the 512-token model limit: 0 in every variant. The chars / 4 estimate is on the safe side for this corpus.

Sanity queries (`python -m rag.index --sanity`), top result per variant:

| Query | V1 | V2 | V3 |
|---|---|---|---|
| how is churn calculated | KPI-007 whole-doc part, 0.784 | KPI-007 Formula chunk, 0.789 | KPI-007 whole doc, 0.781 |
| KPI-014 | SOP-02, 0.648 (miss) | SOP-07, 0.700 (miss) | POL-04 glossary, 0.650 (miss) |
| who owns the customer 360 dashboard | CAT-02, 0.712 (hit) | KPI-011 Dashboards section, 0.775 (miss) | CAT-02, 0.710 (hit) |

Findings:

1. Small chunks win on specific questions. For "how is churn calculated", V2 returns the Formula chunk first, then Definition and Caveats. The V1 and V3 chunks are close behind but carry the whole document.
2. The deprecated KPI-007-V1 ranks second in V1 and V3 (0.746 and 0.743), right below the Certified KPI-007. Similarity alone cannot tell current from deprecated. This needs a metadata filter (certification) or a reranker.
3. Vector search fails on the exact code "KPI-014" in all three variants. Scores are flat (0.65 to 0.70) and no KPI-014 chunk is in the top 3. Embeddings capture meaning, not exact strings. This is the case for BM25 in Step 1.6.
4. V2 fails the owner question. Many small "Dashboards" section chunks in KPI files mention the Customer 360 Dashboard and outscore the catalog row that actually holds the owner. V1 and V3 find CAT-02 first. No single variant wins everything.
5. Scores sit in a narrow band (about 0.65 to 0.79), as in the smoke test. Rank results; do not set a similarity threshold.

## Step 1.6 results: BM25 keyword search (real run)

Code: `src/rag/bm25.py` (tokenizer keeps `kpi-014` whole; `bm25_search(variant, query, k, where, stem)`; same filter idea as Chroma). Run: `python -m rag.bm25 --sanity` (add `--stem` for the suffix stemmer). Tests: `tests/test_bm25.py`.

Top result per variant (vector result from Step 1.5 for comparison):

| Query | Vector (V1 / V2 / V3) | BM25 (V1 / V2 / V3) |
|---|---|---|
| how is churn calculated | KPI-007 / KPI-007 Formula / KPI-007 | KPI-011 (KPI-007 is 2nd) / KPI-005 Conversion Rate (KPI-007 not in top 3) / KPI-011 (KPI-007 2nd) |
| KPI-014 | SOP-02 / SOP-07 / POL-04 (no KPI-014 chunk) | CAT-14 / CAT-14 / CAT-14 (catalog rows that list KPI-014; KPI-014 file is 4th in V1 and V3, absent in V2) |
| who owns the customer 360 dashboard | CAT-02 / KPI-011 Dashboards section / CAT-02 | FAQ-01 (CAT-02 is 3rd) / KPI-011 Dashboards section / FAQ-01 (CAT-02 is 3rd) |

Findings:

1. BM25 alone is worse than vector on natural-language questions. For "how is churn calculated", the words "how", "is" and "calculated" are common ("Calculated daily" appears in many KPI files), so Conversion Rate and Customer Lifetime Value outrank the Churn Rate chunk. In V2 the current KPI-007 is not in the top 3, but the deprecated KPI-007-V1 is. Keyword search also cannot tell Certified from Deprecated.
2. BM25 helps on the code "KPI-014", but not as expected. It finds the catalog rows that list KPI-014 (marketing_spend, Marketing Effectiveness Dashboard, customers), which is useful, but they outrank the KPI-014 definition because BM25 favours short chunks (32 to 38 tokens against 172 for the KPI file).
3. Gap found in V2: none of the 7 V2 chunks of KPI-014 contain the text "KPI-014". The title line `# Title (KPI-014)` is dropped and the header is only `Title | Section`, so the code exists only in metadata. This explains why neither vector nor BM25 can find the KPI-014 file itself in V2. A strict `xfail` test records this. Proposed fix (needs a decision, it changes the locked chunk header and needs a re-embed): header `{title} ({doc_id}) | {section}`.
4. Stemming ("owns" matches "owner") did not help: "owner" appears in every document's Owner line, so it carries almost no weight. CAT-02 even dropped out of the top 3. The stemmer stays as an off-by-default option.
5. Neither method wins everywhere: vector wins on meaning, BM25 surfaces exact codes. This is the case for hybrid search with RRF in Step 2.3.

Note: with 4 test chunks or fewer, a word found in only 1 of 2 chunks gets a BM25 rarity score of exactly 0 and is dropped. Unit tests need at least 4 chunks.

## M1 hands-on check: overlap (real run)

Prediction: raising V1 overlap from 60 to 200 tokens makes the chunk count go up. Result: 52 became 53 (run without changing any file, by setting `c.OVERLAP_TOKENS = 200` in memory). The increase is small because most documents are shorter than one 400-token window (average about 240 tokens) and stay a single chunk whatever the overlap; only the few long documents (for example the POL-04 glossary) split, and a bigger overlap makes those windows advance in smaller steps. Units are tokens, not words.

## Loader change after the golden-set review (2026-10-14)

Problem: owner, status and version were only metadata, not text. The catalog text dropped its Owner and Status columns, and KPI and SOP files lost them with the YAML header. So a question like "who owns the Marketing Effectiveness Dashboard" had no evidence in any chunk (found while checking reference answers G-024 and G-025). It matters most for the project's core question: who owns it, is it certified.

Fix: `ingest.py` now appends an ownership block from the manifest to every document: `Owner`, `Status`, `Version`, `Effective date`, `Domain`. Catalog rows get the lines directly; every other document gets a final `## Ownership and status` section.

Effect (real run): documents 50 (unchanged). V1 52 chunks (avg 271 tokens), V2 265 chunks (was 230; +35, one section per non-catalog document), V3 52 chunks (avg 273, max 416). Tests 46 pass; the golden-set validator passes, including G-024 and G-025.
