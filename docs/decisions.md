# Decisions (locked Day 1)

| # | Decision | Choice | Why |
|---|---|---|---|
| 1 | LLM | Gemini API free tier: Flash-class for answers, strongest free-tier model as judge. All calls go through `llm.complete()` | Free, enough for the prototype. One wrapper = swap provider (Anthropic, Bedrock) by changing one file |
| 2 | Embedding model | `BAAI/bge-small-en-v1.5`, local | Free, fast on CPU, 384 dims. Limit: 512 tokens per chunk |
| 3 | Vector store | Chroma, persistent on disk | Local, free, metadata filters |
| 4 | Stack | Python + plain libraries, no LangChain | I must be able to explain every line |
| 5 | Repo | Private until done, then public | Show a finished README |
| 6 | Company | "Kestrel Retail Group" (fictional) | Rich KPIs, clearly synthetic |
| 7 | Demo | Streamlit app with a Retrieval Inspector | Shows hybrid + rerank visually |
| 8 | Chunk header | `{title} ({doc_id}) \| {section}` on every chunk, all variants | Found in Step 1.6: V2 chunks of KPI-014 never contained the text "KPI-014", so neither BM25 nor the embedding could find the file by its code. Changed 2026-10-14, before the golden-set evaluation |
| 9 | Ownership text | Loader appends Owner, Status, Version, Effective date, Domain (from the manifest) to every document's text | Found while grounding golden answers: these facts were metadata only, so no chunk could answer "who owns X / is X certified". Changed 2026-10-14, before the M2 evaluation |
| 10 | Retrieval default | Chunking V1 + vector search, top 5 | Step 2.3 and 2.4: hybrid lost to vector on dev, rerank was mixed. V1 and V3 tie on dev, V1 kept as the reference. Evidence: `results/experiments.md` |
| 11 | Hybrid retrieval | RRF with equal weights, k=60, kept as optional code (`--retriever hybrid`) | Lost to vector on dev for V1, V2 and V3 (BM25 is the weaker ranker and pulls FAQ-01 into the top 5). No tuning of weights or k on 24 dev questions: that would fit noise |
| 12 | Reranker | `cross-encoder/ms-marco-MiniLM-L-6-v2` over the vector top 50, optional (`--rerank cross-encoder`) | Dev mixed, holdout better on only 8 questions, about 50x latency, FAQ-01 appears more often. Decide on end-to-end answer quality in Step 3.1. It does not know certification or authority |
| 13 | Model IDs | `LLM_MODEL=gemini-3.5-flash-lite`, `JUDGE_MODEL=gemini-3.8-flash` (fallback `gemini-3.6-flash`) | Current stable IDs on the Gemini models page (2026-10-16); the judge returned a 503 once. Recheck IDs before the Step 3.1 run |
| 14 | Model output shape | JSON `{answer, citations, refused}` at temperature 0, checked with stdlib `json` (not Pydantic) | One less dependency; the shape check is a few lines and tested. Output cap 800 tokens (thinking tokens were 0), revisit after Step 3.1 |
| 15 | Citation contract V1 | Every cited ID must be a retrieved chunk ID (exact match); `refused=True` means no citations; `refused=False` means at least one. Returns a list of problems | Checks form only (provenance and consistency). It cannot prove a chunk supports the claim; that is judged in Step 3.1. One retry on a failed check is implemented in `ask()` (step 2.6A, see row 16) |
| 16 | Pipeline behaviour | `ask()` retries once, and only when citation validation fails (provenance or consistency). A second citation failure becomes the refusal with `policy_refusal=True`. Every model attempt is kept in `attempts` and in the trace. Retrieval errors, generation errors (including on the retry), and support, completeness or governance problems are not retried. Every call appends one line to `results/traces.jsonl` | Keeps results auditable and failures diagnosable. The retry is verified with forced failures in unit tests only; no real Gemini run has failed validation yet. `traces.jsonl` is tracked in git for now (small); revisit in Step 3.1 |
| 17 | Governance approach | Label each context chunk with certification; prompt says Certified and current sources govern and conflicts must be named; keep Deprecated chunks in context | Retrieval and rerank cannot enforce authority. G-013 and G-002 need the answer to say v1 is deprecated. Code checks and Certified-first ordering come in Step 2.6 |
| 18 | Run logging | Log a formal run only on a clean commit; keep dirty runs and mark reruns | Runs 15 to 17 and 21 carry a dirty sha; reruns 18 to 20 and 22 are the record |
| 19 | Judge model | Judge = `gemini-3.5-flash-lite`, always passed with `--judge-model gemini-3.5-flash-lite --pause 5`. Row 13's `gemini-3.8-flash` is not used for the judge | Free tier only (no billing). `gemini-3.8-flash` and `gemini-3.6-flash` allow 20 requests a day, which cannot cover about 130 to 150 judge calls; flash-lite allows 500 a day and 15 a minute. Caveat: the judge and the answer model are the same model, so it may favour its own style; the hand-grade check below is the test. Sanity check (planted failures and positive controls): 9 of 9 passed. A per-day quota error now stops a batch and prints when it resets. Switching judge model rejudges every record, so one comparison never mixes judges |
| 20 | Judge validation (Step 3.1) | Hand-graded 10 dev answers blind (3 trap questions), then compared with the judge. Bar fixed before any number: at least 85% agreement on key facts and at least 8 of 10 on faithfulness. First result: key facts 80.6% over 31 (bar missed), faithfulness 10 of 10. All 6 misses were one answer (G-005, v1): the key facts were role titles ("Head of Finance Analytics") but the question asks for teams, and v1 answered with team names, so the judge scored 0 of 6 while v2, which repeated "Head of", scored 6 of 6. Fix: G-005 key facts changed to team names (dev only, same for both versions), G-005 rejudged for v1 and v2 only, nothing else changed. Second result: 100% over 31 facts, kappa 1.0, faithfulness 10 of 10 | The bar was not moved and the human grades were not changed. The defect was in the rubric, not the judge, but the fix was made after seeing results, so both figures are kept (80.6% then 100%). Limits: 10 answers, and only 2 of 31 human grades were n, so leniency is weakly tested. Dev report after the fix: coverage v1 75.6% (59 of 78) and v2 79.5% (62 of 78); answers with every fact 16 and 18 of 24; faithfulness 100% and 0 unsupported claims for both; v2 output +13% tokens |
| 21 | Holdout protocol | Rubric and prompts locked before the holdout. Holdout key facts were scanned before any holdout answer existed: no G-005-type problem found, nothing edited. Run order: commit, then v1 holdout, then v2 holdout, then compare, then decide. No change to v2, the prompts, the rubric or the pass rule after seeing holdout results. Pass rule (set 2026-10-21): v2 generalizes if, on the holdout, its key-fact coverage is at least v1's, faithfulness is not lower, there are no new wrong refusals and no unsupported claims. If it does, v2 becomes the default. If it does not improve, keep v1 and document the negative result. If it improves coverage but adds other problems, investigate before adopting | Known soft spots in the locked holdout rubric, reported as limits and not fixed: G-004 (terse facts "KPI-020" and "Provisional" can fail an answer that says "20 KPIs, 5 Provisional"), G-028 (compound pipe-style key facts that ask for due date and status beyond the question), G-032 ("within 2 hours" does not check the warning-banner action). All three treat v1 and v2 alike. The holdout has 8 answerable questions, so it can confirm or contradict the dev direction but not prove it. Certified-first ordering stays unimplemented unless later evidence supports it |
